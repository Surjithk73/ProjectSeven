# Run the APIShield CinemaFlow demo

**Recommended: laptop + phone.** Use [PHONE-DEMO.md](PHONE-DEMO.md) and double-click `Start Phone Demo.bat`. Only the laptop needs developer tools. The instructions below retain the separate two-Windows-machine deployment option.

For a complete repeat after a merged migration, use **Reset Phone Demo.bat**, then **Start Phone Demo.bat**. Reset archives the old local workspace and creates a fresh V1 GitHub rehearsal branch; new PRs and deployment use that branch. See the complete-reset section in the phone guide. The provider-only reset command below is not a complete phone-demo reset.

## 1. Publish the prepared APIShield branch (System A)

Open PowerShell in `C:/Users/surji/ProjectSeven`:

```powershell
git status --short
git switch feature/cinemaflow-multi-provider
git push -u origin feature/cinemaflow-multi-provider
```

This publishes the prepared branch and preserves main. It does not merge it. System B must use this feature branch until it is merged into ProjectSeven main; the current main snapshot does not contain the new demo tooling.

## 2. Merge the initial CinemaFlow baseline

Sign into GitHub as `surjk73`. Open https://github.com/Surjithk73/APIGuardTesting/pull/2, review the code and checks, approve, and merge when satisfied. Wait for the `cinema-client` workflow on APIGuardTesting main to succeed after the merge. The deployment helper requires the successful check on the exact main revision, not only the PR's checks. This one-time setup PR contains the original V1 client; later migration PRs must be generated by APIShield.

## 3. Prepare the source and environments

System A runs APIShield/Gemini. System B runs CinemaFlow, both providers and the deployment helper. Both are Windows computers on a directly reachable Wi-Fi/LAN. Python 3.11+, Git and GitHub CLI are prerequisites. Node/npm is needed on A for the APIShield frontend. The managed Google JSON stays on A; do not copy it to B.

On B, obtain the published `feature/cinemaflow-multi-provider` branch of https://github.com/Surjithk73/ProjectSeven in its ProjectSeven folder. Open PowerShell **inside that folder**. All commands below are relative to the ProjectSeven folder on the machine where they run.

Set project-local temporary/cache directories before installing dependencies:

```powershell
New-Item -ItemType Directory -Force .apishield/cinema/temp | Out-Null
$env:TEMP = (Resolve-Path .apishield/cinema/temp).Path
$env:TMP = $env:TEMP
$env:PIP_CACHE_DIR = Join-Path (Get-Location) '.apishield/cinema/cache/pip'
$env:npm_config_cache = Join-Path (Get-Location) '.apishield/cinema/cache/npm'
```

If the Python environment is absent, create it. Install requirements on a fresh checkout:

```powershell
py -3 -m venv venv
./venv/Scripts/python.exe -m pip install -r requirements.txt
```

Skip environment creation on A if its existing venv already works. On A, prepare the frontend if needed:

```powershell
npm --prefix frontend ci
npm --prefix frontend run build
```

Run `./demo/scripts/check_environment.ps1`. Existing installations on A need not be reinstalled. New demo state, releases, logs and test workspaces live in `.apishield/cinema`; that directory is ignored by Git. Existing managed credentials remain in their established location and are read rather than relocated.

## 4. Authenticate the correct GitHub account on each machine

On A, `gh api user --jq .login` must return `Surjithk73`.

On B, authenticate locally as `surjk73`:

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh api user --jq .login
```

If the CLI has multiple accounts, select the intended account locally using `gh auth switch`. B must report `surjk73`, matching the trusted receipt author in the configuration. Do not share passwords or tokens in chat or place them in the demo JSON.

## 5. Start the actual deployment demo on B

If the development preview is already running on B, stop that managed preview first:

```powershell
./demo/scripts/stop_system_b.ps1
```

Wait for its ports to be released. A first-time B with no running preview skips that command. Prepare the private project-local deployment configuration once:

```powershell
New-Item -ItemType Directory -Force .apishield/cinema | Out-Null
Copy-Item demo/deployment/system-b.example.json .apishield/cinema/system-b.json
./demo/scripts/start_system_b.ps1 -DeploymentConfig .apishield/cinema/system-b.json
```

Do not overwrite an existing customized system-b.json; reuse it. Defaults already identify the correct repository, main branch, publisher, `surjk73`, local provider ports and project-local release directory.

The helper fetches main, creates its release environment, runs tests and starts the client. First startup can take longer because requirements are installed. Open `http://127.0.0.1:8100` on B once startup completes. Confirm both providers are V1 in the API providers tab, then make an initial booking.

Copy the LAN client link printed by the launcher. B generates its own link; the link from A's earlier preview is not B's address. For alternatives:

```powershell
./venv/Scripts/python.exe -B -m demo.setup connection-info
```

If A cannot open B's link, check Windows Private-profile TCP access to 8100, 8101 and 8102, and ensure the Wi-Fi permits peer connectivity. The launcher does not change firewall policy. These are LAN links, not public internet hosting.

**For the merge/deployment demo, always include `-DeploymentConfig`.** Starting B without it serves the V1 template directly and does not run the merged-release deployment helper.

## 6. Register and start APIShield on A

After the initial client PR is merged, create the clean local source checkout once:

```powershell
New-Item -ItemType Directory -Force .apishield/cinema | Out-Null
git clone https://github.com/Surjithk73/APIGuardTesting.git .apishield/cinema/client-source
./demo/scripts/start_system_a.ps1
```

If that checkout already exists, preserve changes and use `git -C .apishield/cinema/client-source pull --ff-only` rather than cloning over it. A's source must be clean and match main. Do not manually apply candidate edits to it.

Paste B's printed CinemaFlow link at the prompt. Open `http://127.0.0.1:8002/?project=cinemaflow`. Stop an older app on port 8002 yourself before launch; the launcher does not kill it. If necessary register without starting, then use a free app port:

```powershell
./demo/scripts/start_system_a.ps1 -SetupOnly
./demo/scripts/open_system_a.ps1 -Port 8005
```

Use the setup command only for first registration. For later starts use `./demo/scripts/open_system_a.ps1` (or `-Port 8005`), preserving the registered state.

In CinemaFlow Integration, expand Repository and deployment settings. Click **Connect GitHub publisher**, confirm APIGuardTesting/main and publisher `Surjithk73`, and confirm the deployment account is `surjk73`. Keep **Manual** mode initially. Check AI connection using the existing settings panel if needed. Both provider cards should become reachable/up to date after a check.

## 7. Present the manual migration cycle

1. On B, book an available V1 seat and show its confirmation.
2. In B's API providers tab, switch **CinemaPay** to V2; leave theatre V1.
3. Return to Book tickets on B and attempt another booking. Show the compatibility error.
4. On A, click **Check for API Changes**. Inspect changed payment endpoints and affected code/graph.
5. Click **Ask AI to Update**. Show Agent activity progressing through analysis, generated checks, candidate generation and validation. If generation/validation fails, inspect the retained error and use explicit Retry; do not claim it succeeded.
6. After validation, prepare/view the GitHub draft preview, inspect the diff and publish the PR.
7. On GitHub as `surjk73`, review the new PR, mark ready if it is still a draft, approve and merge after checks pass.
8. Wait for successful main CI. B polls every 10 seconds and installs the exact eligible merge revision; dependency installation/restart can add time.
9. On A, wait for **Deployed and verified** evidence. Show matching merge/running revisions. Only an authenticated successful receipt advances the provider baseline and clears current impact.
10. Refresh B's client, select new available seats and book successfully. Open the current semantic graph on A to show the accepted deployed state. Historical run graphs remain historical evidence.

The provider version controls must be used on B through its local URL; admin changes are deliberately loopback-only.

## 8. Present automatic mode

After payment V2 has been deployed and verified, switch A's update mode to **Automatic**. On B, switch Grand Cinema/theatre to V2. With five-minute monitoring enabled, APIShield detects and processes the change automatically; **Check now** can trigger immediate detection without waiting for the interval. It generates, validates and publishes a PR. `surjk73` still reviews/merges it. B then deploys and verifies. Automatic mode never auto-merges.

## 9. Stop and replay

Stop B with `./demo/scripts/stop_system_b.ps1` and wait for its managed processes to exit. To clear only provider/demo booking state, run `./demo/scripts/reset_rehearsal.ps1` afterward. This preserves source, PRs and Git history.

**Reset is not a complete migration replay.** Resetting providers to V1 does not undo a V2 client already merged/deployed. A fresh full replay requires a reviewed forward restoration of the V1 client baseline plus a clean deployment/monitoring baseline. Do not force-push main or assume restarting reverts the source. The first live demo can demonstrate payment V2 followed by theatre V2 without a reset.
